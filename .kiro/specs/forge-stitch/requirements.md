# Requirements Document

## Introduction

ForgeStitch is an AI-powered Atlassian Forge application built for the Kiroween Hackathon (Frankenstein category). It stitches together Jira issue tracking, Confluence documentation, and automated sprint reporting into a unified developer assistant. The application is deployed entirely within the Atlassian Forge platform, using Forge AI (Rovo) APIs for all AI capabilities with no external LLM keys required. ForgeStitch surfaces two UI experiences: a per-ticket Jira Issue Panel and a full Project Dashboard Page. A runtime Demo/Sandbox Mode toggle allows users to switch between live Forge API data and bundled sample data without reinstalling the app.

## Glossary

- **ForgeStitch**: The Atlassian Forge application described in this specification.
- **Forge AI**: The Atlassian Rovo / Forge AI APIs used as the AI backend within the Forge platform.
- **Issue Panel**: A Custom UI React panel rendered inside a Jira issue view, surfacing per-ticket documentation links, AI actions, and health indicators.
- **Project Dashboard**: A full-page Custom UI React application rendered at the Jira project level, showing sprint health metrics, blocker summaries, and aggregated documentation.
- **Tech Spec Page**: A Confluence page generated by ForgeStitch that documents a Jira issue's details, acceptance criteria, and AI-synthesized description.
- **Changelog Page**: A Confluence page generated or updated by ForgeStitch that records the change history for a Jira issue or project.
- **Sprint Pulse**: The aggregated sprint health summary produced by ForgeStitch, including stall/blocker detection and an executive summary with action items.
- **Stitcher**: The core ForgeStitch backend resolver that combines Jira and Confluence data, calls Forge AI, and returns structured results to the UI.
- **Demo Mode**: A runtime UI toggle that switches ForgeStitch from live Forge API data to bundled sandbox data without requiring reinstallation.
- **Sandbox Data**: Bundled, realistic sample Jira and Confluence data used when Demo Mode is active.
- **Upsert**: The Confluence publishing strategy where ForgeStitch updates an existing linked page in-place or creates a new page if none exists.
- **Manifest**: The Atlassian Forge `manifest.yml` file declaring app scopes, modules, and permissions.
- **Scopes**: OAuth permission scopes declared in the Manifest that govern ForgeStitch's access to Jira and Confluence APIs.

## Requirements

### Requirement 1: Jira Issue Panel

**User Story:** As a developer, I want a Jira Issue Panel that shows me linked Confluence documentation and AI-generated actions for the current ticket, so that I can access all relevant context without leaving the issue view.

#### Acceptance Criteria

1. THE Issue Panel SHALL render as a Jira issue glance or issue panel Custom UI module for every Jira issue within the installed project.
2. WHEN the Issue Panel loads for a Jira issue, THE Issue Panel SHALL display the issue summary, status, assignee, and priority fetched from Jira.
3. WHEN a Confluence Tech Spec Page or Changelog Page is linked to the current issue, THE Issue Panel SHALL display the page title and a clickable link to that page.
4. IF no Confluence page is linked to the current issue, THEN THE Issue Panel SHALL display a prompt indicating that no documentation exists and offer an action to generate it.
5. THE Issue Panel SHALL provide a "Generate Tech Spec" action button that triggers Automated Technical Spec generation for the current issue.
6. THE Issue Panel SHALL provide a "Generate Changelog" action button that triggers Automated Changelog generation for the current issue.
7. WHEN an AI action is in progress, THE Issue Panel SHALL display a loading indicator until the action completes or fails.
8. IF an AI action fails, THEN THE Issue Panel SHALL display an error message describing the failure and allow the user to retry.

### Requirement 2: Project Dashboard Page

**User Story:** As a project lead, I want a Project Dashboard that aggregates sprint health, blocker summaries, and documentation links across the entire project, so that I can monitor team progress and act on risks from a single view.

#### Acceptance Criteria

1. THE Project Dashboard SHALL render as a full-page Jira project page Custom UI module accessible from the project sidebar.
2. WHEN the Project Dashboard loads, THE Project Dashboard SHALL display the active sprint name, start date, end date, and completion percentage derived from Jira sprint data.
3. WHEN the Project Dashboard loads, THE Project Dashboard SHALL list all issues in the active sprint grouped by status (e.g., To Do, In Progress, Done).
4. WHEN the Project Dashboard loads, THE Project Dashboard SHALL display the Sprint Pulse summary generated by the Stitcher.
5. THE Project Dashboard SHALL provide a "Refresh Sprint Pulse" action button that re-invokes the Stitcher to regenerate the Sprint Pulse summary on demand.
6. WHEN a "Refresh Sprint Pulse" action is in progress, THE Project Dashboard SHALL display a loading indicator until the action completes or fails.
7. IF a "Refresh Sprint Pulse" action fails, THEN THE Project Dashboard SHALL display an error message and allow the user to retry.

### Requirement 3: Automated Technical Spec Generator

**User Story:** As a developer, I want ForgeStitch to automatically generate a formatted technical specification for a Jira issue and publish it to Confluence, so that I do not have to write boilerplate documentation manually.

#### Acceptance Criteria

1. WHEN a "Generate Tech Spec" action is triggered for a Jira issue, THE Stitcher SHALL read the issue summary, description, acceptance criteria fields, and all comments from Jira.
2. WHEN the Stitcher has retrieved Jira issue data, THE Stitcher SHALL invoke Forge AI to synthesize a structured technical specification document containing a summary, context, acceptance criteria, and implementation notes sections.
3. WHEN the Forge AI response is received, THE Stitcher SHALL format the content as a valid Confluence Storage Format document.
4. WHEN a linked Tech Spec Page already exists for the issue, THE Stitcher SHALL update the existing Confluence page in-place using the upsert strategy.
5. IF no linked Tech Spec Page exists for the issue, THEN THE Stitcher SHALL create a new Confluence page and store the page URL as a link on the Jira issue.
6. WHEN the Confluence page is successfully created or updated, THE Stitcher SHALL return the page title and URL to the Issue Panel.
7. IF the Forge AI invocation fails, THEN THE Stitcher SHALL return a structured error indicating the failure stage (data retrieval, AI generation, or Confluence publish) without publishing partial content.

### Requirement 4: Automated Changelog Generator

**User Story:** As a developer, I want ForgeStitch to generate and maintain a changelog for a Jira issue on Confluence, so that stakeholders can track how the ticket evolved over time without reading every comment.

#### Acceptance Criteria

1. WHEN a "Generate Changelog" action is triggered for a Jira issue, THE Stitcher SHALL retrieve the issue's status transition history, comment history, and field change history from Jira.
2. WHEN the Stitcher has retrieved issue history data, THE Stitcher SHALL invoke Forge AI to synthesize a chronological changelog in human-readable prose organized by date.
3. WHEN the Forge AI response is received, THE Stitcher SHALL format the changelog as a valid Confluence Storage Format document.
4. WHEN a linked Changelog Page already exists for the issue, THE Stitcher SHALL update the existing Confluence page in-place using the upsert strategy.
5. IF no linked Changelog Page exists for the issue, THEN THE Stitcher SHALL create a new Confluence page and store the page URL as a link on the Jira issue.
6. WHEN the Confluence page is successfully created or updated, THE Stitcher SHALL return the page title and URL to the Issue Panel.
7. IF the Jira history retrieval fails, THEN THE Stitcher SHALL return a structured error and not invoke Forge AI or publish to Confluence.

### Requirement 5: Sprint Pulse & Blocker Stitcher

**User Story:** As a project lead, I want ForgeStitch to analyze the active sprint, detect stalled or blocked tickets, and produce an executive summary with action items, so that I can quickly understand sprint health and prioritize unblocking work.

#### Acceptance Criteria

1. WHEN a Sprint Pulse generation is triggered, THE Stitcher SHALL retrieve all issues in the active sprint from Jira including their status, assignee, priority, and labels.
2. WHEN sprint issue data is retrieved, THE Stitcher SHALL identify stalled issues, defined as issues with status "In Progress" that have had no activity (comment, transition, or field update) for more than 2 business days.
3. WHEN sprint issue data is retrieved, THE Stitcher SHALL identify blocked issues, defined as issues carrying a "blocked" label or having a blocking issue link in Jira.
4. WHEN stalled and blocked issues are identified, THE Stitcher SHALL invoke Forge AI to generate an executive sprint summary including: overall sprint health rating, a list of at-risk issues with assignees, and a prioritized list of recommended action items.
5. WHEN the Forge AI response is received, THE Stitcher SHALL return the structured Sprint Pulse result to the Project Dashboard for display.
6. IF no active sprint exists in the project, THEN THE Stitcher SHALL return a status indicating no active sprint and THE Project Dashboard SHALL display an appropriate message.
7. IF the Forge AI invocation for Sprint Pulse fails, THEN THE Stitcher SHALL return the raw aggregated sprint data without an AI summary and THE Project Dashboard SHALL display the raw data with a notice that AI summarization is unavailable.

### Requirement 6: Demo / Sandbox Mode

**User Story:** As a hackathon demonstrator, I want a runtime toggle that switches ForgeStitch between live Atlassian API data and bundled sandbox data, so that I can demonstrate the app reliably without depending on a live Jira project.

#### Acceptance Criteria

1. THE Project Dashboard SHALL display a Demo Mode toggle switch in a consistently visible location within the UI.
2. THE Issue Panel SHALL display a Demo Mode toggle switch in a consistently visible location within the UI.
3. WHEN Demo Mode is enabled, THE Stitcher SHALL substitute all Jira API calls with responses drawn from bundled Sandbox Data without making any network requests to Jira or Confluence APIs.
4. WHEN Demo Mode is enabled, THE Stitcher SHALL substitute all Confluence API calls with responses drawn from bundled Sandbox Data without making any network requests to Jira or Confluence APIs.
5. WHEN Demo Mode is enabled, THE Stitcher SHALL still invoke Forge AI for content generation unless Forge AI is also unavailable, in which case THE Stitcher SHALL use pre-generated AI response fixtures from Sandbox Data.
6. WHEN Demo Mode is disabled, THE Stitcher SHALL revert to live Forge API calls immediately on the next user action without requiring reinstallation.
7. THE Sandbox Data SHALL contain at least one complete sample sprint with a minimum of five issues covering the statuses: To Do, In Progress (active), In Progress (stalled), Blocked, and Done.
8. THE Sandbox Data SHALL contain at least two sample Confluence pages representing a Tech Spec Page and a Changelog Page linked to sandbox Jira issues.
9. WHEN Demo Mode is active, THE Issue Panel and THE Project Dashboard SHALL display a visible "Demo Mode" badge so users can distinguish sandbox data from live data.

### Requirement 7: Forge Manifest and Permissions

**User Story:** As an Atlassian Marketplace reviewer, I want ForgeStitch to declare only the minimum required API scopes in its manifest, so that the app does not request permissions beyond what its features need.

#### Acceptance Criteria

1. THE Manifest SHALL declare the `read:jira-work` scope to allow ForgeStitch to read Jira issue data, sprint data, and issue history.
2. THE Manifest SHALL declare the `write:confluence-content` scope to allow ForgeStitch to create and update Confluence pages.
3. THE Manifest SHALL declare the `read:confluence-content.all` scope to allow ForgeStitch to read existing Confluence page content for the upsert check.
4. THE Manifest SHALL declare the `storage:app` scope to allow ForgeStitch to persist Confluence page link metadata per Jira issue using Forge Storage.
5. THE Manifest SHALL NOT declare any scope beyond those required by the features defined in this specification.
6. THE Manifest SHALL declare the Issue Panel module under a supported Jira Custom UI glance or panel extension point.
7. THE Manifest SHALL declare the Project Dashboard module under a supported Jira project page Custom UI extension point.

### Requirement 8: Error Handling

**User Story:** As a developer using ForgeStitch, I want all errors from Jira, Confluence, and Forge AI calls to be caught and surfaced clearly, so that I know what went wrong and can take corrective action.

#### Acceptance Criteria

1. WHEN a Jira API call returns a non-2xx HTTP status, THE Stitcher SHALL catch the error, log the HTTP status and endpoint, and return a structured error object to the calling UI component.
2. WHEN a Confluence API call returns a non-2xx HTTP status, THE Stitcher SHALL catch the error, log the HTTP status and endpoint, and return a structured error object to the calling UI component.
3. WHEN a Forge AI call returns an error, THE Stitcher SHALL catch the error, log the error message, and return a structured error object to the calling UI component.
4. WHEN the Issue Panel receives a structured error object, THE Issue Panel SHALL display a human-readable error message derived from the error object without exposing raw API error payloads to the user.
5. WHEN the Project Dashboard receives a structured error object, THE Project Dashboard SHALL display a human-readable error message derived from the error object without exposing raw API error payloads to the user.
6. THE Stitcher SHALL not throw unhandled exceptions; IF an unexpected error occurs, THEN THE Stitcher SHALL catch it, log the stack trace, and return a generic structured error object.

### Requirement 9: Unit Tests for Core Logic

**User Story:** As a developer maintaining ForgeStitch, I want unit tests covering the Stitcher's core formatting and stitching logic, so that regressions are caught before deployment.

#### Acceptance Criteria

1. THE test suite SHALL include unit tests for the Confluence Storage Format document builder, verifying that given valid input data the builder produces well-formed output.
2. THE test suite SHALL include unit tests for the stall-detection logic, verifying that issues with no activity within the stall threshold are correctly identified as stalled.
3. THE test suite SHALL include unit tests for the blocker-detection logic, verifying that issues with a "blocked" label or a blocking issue link are correctly identified as blocked.
4. THE test suite SHALL include unit tests for the Demo Mode data-substitution logic, verifying that when Demo Mode is active all Jira and Confluence API calls are replaced with Sandbox Data responses.
5. WHEN any unit test fails, THE test suite SHALL report the failing test name and the expected versus actual values.
